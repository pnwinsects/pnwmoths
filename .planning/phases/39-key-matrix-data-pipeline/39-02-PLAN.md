  <action>
    Create `scripts/copy-key-matrix.ts` mirroring `copy-parquet.ts` but for a single file: import
    `copyFile, mkdir` from `node:fs/promises` and `resolve` from `node:path`,
    `await mkdir(resolve('_site'), { recursive: true })`, then
    `await copyFile(resolve('data/key-matrix.json'), resolve('_site/key-matrix.json'))` and log
    the copy. It must run post-Eleventy because eleventy-plugin-vite wipes `_site/` during the
    build. No `main()`/test seam needed (covered by the build-chain integration in Task 3).

    Create `scripts/check-key-weight.ts` per Pattern 8: import `readFileSync, existsSync` from
    `node:fs` and `gzipSync` from `zlib` (Node built-in, no new dep). Default
    `BUDGET_BYTES = 50 * 1024` (D-06) and `ARTIFACT = '_site/key-matrix.json'`, but read both
    from `process.env['KEY_BUDGET_BYTES']` and `process.env['KEY_MATRIX_PATH']` respectively
    (falling back to the defaults) so the gate is testable against fixtures without touching the
    real `_site/`. If the artifact is absent, `console.error` and `process.exit(1)` (Pitfall 4:
    it runs only after the copy). Read the file, `gzipSync` it, and if `gz.length > BUDGET_BYTES`
    print a FAIL line with the measured KB and `process.exit(1)`; otherwise print an OK line.
    Unlike `check-page-weight.ts` (which only warns), this gate exits non-zero on failure — it is
    a hard budget gate (KEY-04).

    Create `scripts/check-key-weight.test.ts` (node:test) that exercises the gate via `execSync`
    using the env overrides: write a small under-budget JSON to a temp path, point
    `KEY_MATRIX_PATH` at it, and assert the gate exits 0; write a > 50 KB-gzip blob (or set a
    tiny `KEY_BUDGET_BYTES`) and assert `execSync` throws (non-zero exit). Clean up temp files in
    the test.
  </action>
  <verify>
    <automated>node --test scripts/check-key-weight.test.ts</automated>
  </verify>

    - `node --test scripts/check-key-weight.test.ts` passes both the under-budget (exit 0) and over-budget (exit 1) cases.
    - The gate honors `KEY_MATRIX_PATH` / `KEY_BUDGET_BYTES` env overrides (defaults `_site/key-matrix.json` and `50*1024`).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| build artifact → `_site/` → deploy | `copy-key-matrix.ts` copies a build-generated file into the published directory; both source and destination are build-machine-local |
| CI workflow chain | `deploy.yml` / `pr-check.yml` run the hardcoded build chain; drift between them and `package.json` is the main integrity risk |

This plan is build/CI wiring only — no runtime input, no network ingestion, no new packages.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-39-04 | Tampering | shipped `_site/key-matrix.json` size | mitigate | `check-key-weight.ts` fails the build (exit 1) when gzip > 50 KB, so artifact bloat cannot silently ship (KEY-04) |
| T-39-05 | Repudiation / drift | CI vs local build chain divergence | mitigate | Both `deploy.yml` and `pr-check.yml` updated identically and in sync with `package.json`; verify gate greps both workflows for the three new steps |
| T-39-06 | Denial of service | `check-key-weight.ts` reads a missing artifact | mitigate | `existsSync` guard exits 1 with a clear message if `_site/key-matrix.json` is absent (Pitfall 4 ordering) |
| T-39-SC | Tampering | npm/pip/cargo installs | accept | No package installs — `zlib`, `node:fs`, `node:path` are Node built-ins; nothing added to package.json deps |

No high-severity threats. The byte-budget gate itself is the primary new integrity control.
</threat_model>
