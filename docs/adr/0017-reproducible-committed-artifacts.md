# 0017. Committed build artifacts carry no build timestamp

**Status:** Accepted

## Context

`data/key-matrix.json` and `data/key-coverage-report.json` are generated by
[`scripts/build-key.ts`](../../scripts/build-key.ts) and committed to the repo
([0012](0012-identify-static-key.md) — the Identify key ships as a static artifact, so it has to
exist in the tree rather than be built on demand).

Both embedded an ISO 8601 build timestamp: `meta.generatedAt` in the matrix, `generated` in the
coverage report. That made them differ on every regeneration regardless of whether their inputs
changed, so `git status` was dirty after any build and the diff was pure noise.

That noise actively concealed a real bug. The test suite overwrote both artifacts with
fixture-derived data on every `npm test` run, leaving a key matrix with every `image_filename`
nulled ([#163](https://github.com/pnwinsects/pnwmoths/issues/163)). Because the files always
showed as modified, the corruption was indistinguishable from the usual timestamp churn, and the
only way to tell them apart was to diff with the timestamps stripped:

```sh
git show HEAD:data/key-matrix.json | sed -E 's/"generatedAt":"[^"]*"/"TS"/g' | shasum
```

It went unnoticed long enough to require a cleanup commit (`dc92598d`), and then recurred.

Nothing read either timestamp. `generatedAt` appeared only in the Zod schema, the producer, and
five test fixtures; `key-coverage-report.json` is a maintainer-facing advisory report with no
runtime consumer at all.

## Decision

**Committed build artifacts contain no build timestamp, and must be byte-reproducible from
unchanged inputs.** `generatedAt` is removed from `KeyMatrixMetaSchema`, and `generated` from the
coverage report. Provenance comes from `git log` on the artifact, which is more accurate anyway —
it records when the content actually changed, not when a build last ran.

`scripts/build-key.test.ts` enforces this: two consecutive builds must produce byte-identical
output, and neither artifact may contain a timestamp field.

This applies to any future committed artifact. Non-committed outputs (`_site/`, reports written
outside the repo) are unaffected.

## Consequences

- A dirty `data/` after a build now means the inputs changed. That is a real signal, and
  [#163](https://github.com/pnwinsects/pnwmoths/issues/163)-class bugs surface immediately in
  `git status` instead of hiding.
- Artifact diffs in review show only substantive change.
- The reproducibility test doubles as a determinism guard: if map/set iteration order or any other
  nondeterminism leaks into the emitted JSON, it fails there rather than as mystery churn.
- Removing a required schema field is safe for already-deployed artifacts. `KeyMatrixMetaSchema`
  is a non-strict `zod/mini` object, so a cached `key-matrix.json` still carrying `generatedAt`
  validates fine — the extra key is stripped, not rejected.
- Losing in-file provenance is a deliberate trade. Anyone needing the build time can use
  `git log -1 -- data/key-matrix.json`.

## Alternatives rejected

- **Keep the timestamp, add tooling to diff around it.** Every consumer of the diff — humans,
  review tools, `git status` — would need to know the trick. The bug that motivated this ADR
  survived precisely because that knowledge was not applied by default.
- **Keep the timestamp but round it** (to the day, say). Shrinks the churn without eliminating it,
  and still produces spurious diffs across a date boundary.
- **Stop committing the artifacts and build them at deploy time.** Contradicts
  [0001](0001-static-no-server.md) and [0012](0012-identify-static-key.md): there is no build
  server, and the key must be present as a static file.
